InfraWatch 2.0

Unified observability, incident management and AI-assisted root cause analysis: product and engineering specification

Version 0.1 (draft) Date 9 November 2026 Status Specification, pre-implementation Working title InfraWatch 2.0
Status notice. This document specifies a system that has not yet been built. Every capability described here is a requirement or a design decision, not an existing feature. The acceptance checks in section 10 define when each requirement is considered met.

1. Summary

In most organisations, observability tooling (metrics, logs, dashboards) and IT service management tooling (incident tickets, assignment, post-incident review) are separate products used by separate people. An engineer who sees a problem in a dashboard must manually open a ticket, copy context into it, find the right team, and later reconstruct what happened. Context is lost, response is slower, and the knowledge gained in each incident rarely reaches the next engineer who faces something similar.

InfraWatch 2.0 combines these into one application with four connected stages:

  1. Observe. A shared, read-only view of system health (infrastructure metrics, application metrics, logs, change events) available to all users.
  2. Raise. Production Support reviews an alert-generated draft, or raises an incident directly, attaching observability data and any other evidence.
  3. Collaborate. The incident is visible in the app and emailed to the owning team's group address with the on-call engineer in CC. Teams work in parallel against a seven-state progress bar, and each team lead assigns work within their team.
  4. Learn. No incident can be closed until a runbook has been written, reviewed and approved. Approved runbooks form the knowledge base from which an AI layer predicts probable root causes for future incidents.

The platform is built from scratch with its own collector agent, storage and user interface. It is not layered on Prometheus, Grafana or Loki. ServiceNow integration is optional and secondary: the product has its own ticketing and can synchronise with a ServiceNow instance through the Table API.

Primary objective. A demonstrable, end-to-end portfolio project that shows full-stack, DevOps and applied-AI capability. The architecture keeps the path to a real product open, but the first release is optimised for a credible, reproducible demonstration at small scale.

2. Business case

2.1 Problem

  • Context loss at hand-off. Incident tickets are created by hand, outside the tool where the problem was observed.
  • Slow acknowledgement and resolution. Routing, notification and escalation depend on human memory and manual steps.
  • Alert fatigue and clerical load. On-call engineers spend incident time on ticket hygiene rather than diagnosis.
  • Lost institutional knowledge. Post-incident learning is inconsistent, unstructured, or never written. When people leave, the knowledge leaves with them.
  • Audit exposure. Regulated environments must show that each significant event produced a tracked, owned and reviewed incident.

2.2 Value proposition

Operational

  • One place to see health, raise, assign and resolve.
  • Pre-filled incidents with frozen evidence.
  • Defined SLAs, escalation and on-call rotation.

Knowledge

  • Mandatory, structured runbooks with a controlled root cause taxonomy.
  • Similar-incident retrieval at the moment of creation.
  • Ranked root cause suggestions with cited evidence.

Governance

  • Caller-confirmed closure and rejection path.
  • Immutable audit trail of every change.
  • Role-based visibility, including stakeholder-safe views.

Measurable outcomes

  • Mean time to acknowledge and resolve.
  • Duplicate and repeat-incident rates.
  • Top-k root cause prediction accuracy.

2.3 Market positioning

Several commercial observability vendors offer ServiceNow integrations, and the AIOps category (event correlation, noise reduction, probable-cause analysis) is occupied by established products. InfraWatch 2.0 does not claim a new category. Its position is a single, integrated workflow that joins telemetry, ticketing, enforced post-incident learning and retrieval-grounded AI, in a form that is transparent, self-hostable and demonstrable. The differentiating ideas are the closure gate (no close without an approved runbook), the controlled root cause taxonomy that turns runbooks into clean training labels, and shadow-mode evaluation that makes AI accuracy measurable before it is trusted.

2.4 Portfolio value

The project exercises backend and API design, real-time systems, data modelling for time series, DevOps (containerisation, CI, later cloud deployment), security and access control, and applied AI (retrieval, evaluation, human-in-the-loop). Resume claims must come from reproducible scripts in the repository (check G10.3), not from estimates.

  • Training or fine-tuning a proprietary model

6. Functional specification

6.1 Telemetry collection and storage

  • A lightweight collector agent runs beside monitored hosts or containers and reports infrastructure metrics (CPU, memory, disk, network) at a configurable interval, with a target visibility delay of 15 seconds.
  • A demo application emits application metrics (latency, error rate, request rate) and structured logs carrying correlation identifiers.
  • Change events (deployments, configuration changes, feature-flag changes) are accepted through an authenticated webhook and are shown as markers on charts.
  • The agent buffers locally and retries so that a restart or short network loss does not cause silent data loss beyond a documented buffer size.
  • Metrics and logs are stored in TimescaleDB hypertables with a default retention of 30 days. Incidents, runbooks and audit records are retained indefinitely.
  • A fault-injection command on the demo application produces realistic incidents (CPU saturation, error bursts, a bad deployment, dependency latency) so the platform can be exercised without a production system.

6.2 Dashboards

  • Every registered service has a prebuilt health dashboard (resource usage, request rate, error rate, latency, recent logs, change markers).
  • Users may add, remove and rearrange basic metric panels on a dashboard, and the layout persists per user or per team.
  • The full Grafana-style builder (query editor, variables, many panel types) is explicitly deferred to Phase 3 so that it does not delay the incident and AI loop.

6.3 Alerting

  • Static thresholds: user-defined rules per metric, with a duration condition to suppress transient spikes.
  • Statistical anomaly detection: baseline-deviation detection requiring no manual threshold.
  • AI-suggested thresholds: the model proposes thresholds derived from history. A proposal has no effect until a human approves it.
  • A firing alert creates a draft incident pre-filled with the service, metric snapshot and time range. No notification is sent until Production Support reviews and raises the incident.
  • Repeated firings of the same rule for the same service are deduplicated into the existing draft or incident rather than creating new ones.

These values are defaults (section 11) and are configurable by an Admin. Timers display remaining time and flag breaches.

Teams and assignment

  • An incident can involve several teams at once. Each involved team has its own task with an assignee and a checklist, all under the one shared incident status.
  • A team lead may assign the team's task to any member of that team, and to no one outside it.
  • A team's group email address is configured by an Admin.

Attachments

  • Metric snapshots are frozen at the moment of attachment (chart, exact time range and values) and never change afterwards.
  • Log excerpts are stored as selected lines with their correlation identifiers.
  • Files and screenshots are uploaded to MinIO, subject to a size limit and a file-type allowlist enforced on the server.
  • Links and notes carry external references and free-text context.

6.5 Notifications and on-call

  • Raising an incident sends one email to the involved team's group address, with the current on-call engineer in CC, and posts the incident in the app.
  • Emails are sent on raise, severity change, reassignment to a new team, Resolved and Closed. Routine status steps do not send email.
  • Developers and SREs maintain their team's on-call rotation in the app. The CC always follows the rotation in force at the time.
  • If the on-call engineer does not acknowledge within the escalation timer, the incident escalates to the next person in the rotation and the escalation is recorded.
  • If a team has no on-call set, the Admin is alerted and the group email is still sent.
  • In the MVP, email is delivered to Mailpit. The SMTP target is configuration, so a real provider can be used later without code changes.

6.6 Runbooks

The runbook is the gate between Resolved and Closed, and the primary source of training and retrieval data. It is therefore structured.

FieldRequiredPurpose
TimelineYesDetection, acknowledgement, mitigation and resolution times and key events
Root causeYesFree-text explanation plus a category from the controlled taxonomy
Contributing factorsYesWhat slowed detection or recovery, or enlarged impact
Remediation and preventionYesWhat fixed it, and follow-up actions to prevent recurrence
Workaround appliedYesAny temporary measure and whether it remains in place
Similar incidentsYesLinks to related past incidents, or an explicit statement that none were found

Root cause taxonomy (default list): Code or deploy; Configuration; Capacity or infrastructure; Dependency or third party; Data; Security; Process or human.

Process: the resolver writes the runbook, a lead (or Incident Commander) approves or returns it with comments, and only then does the caller's Close action become available. Approved runbooks are versioned and searchable. Submission with any required field empty is rejected by the server.

6.7 AI layer

Data used

  • Metrics, logs and change events around the incident window.
  • The service catalogue and dependency relationships.
  • Historical incidents and approved runbooks (the retrieval corpus).
  • On-call and assignment history.
  • Candidates for later phases: distributed traces, cloud-provider and third-party status feeds, incident-channel transcripts, business-impact signals.

Design

The AI layer has two tiers. Retrieval: runbooks and incidents are embedded and stored in pgvector; a new incident retrieves its most similar predecessors. Reasoning: a provider-agnostic LLM interface receives the current evidence and the retrieved runbooks and returns a ranked list of probable root causes, each with a confidence value and the specific supporting evidence. The provider can be changed by configuration alone. If the model is unavailable, the incident workflow continues and the interface states that suggestions are unavailable.

Features

  • Similar past incidents shown when an incident is created, with similarity and links.
  • Ranked root cause analysis with confidence and cited evidence (metrics, logs, change events, matched runbooks).
  • Runbook draft pre-filled from the timeline and telemetry for the resolver to edit.
  • Stakeholder comms draft in plain language for the Comms role.
  • Threshold suggestions for alert rules (human approval required).
Human in the loop. Every AI output is labelled as AI-generated, is editable, and is never sent, saved as final, or applied without an explicit human action.

Cold start and data supply

With no history, the model is supplied by three sources used together: a generated synthetic corpus of incidents and runbooks, real incidents produced by live fault injection on the demo application, and an import command for sanitised real past incidents in CSV or JSON.

Evaluation and keeping the data current

  • Shadow mode: predictions are stored silently and compared with the approved runbook's root cause; a scoreboard reports top-k accuracy. User-facing suggestions are enabled only after accuracy meets a target set in advance.
  • Feedback: thumbs up or down on every suggestion, stored against the prediction.
  • Offline benchmark: a held-out set of incidents is reserved for repeatable evaluation.
  • Staleness job: a scheduled check flags services with no recent telemetry, deploy events or runbooks, and notifies the owning team, so that Production Support and SRE keep the data in step with production.

6.8 ServiceNow synchronisation (optional)

  • With a ServiceNow developer instance configured, raising an incident creates the corresponding record through the Table API, and status changes synchronise in both directions.
  • Each synchronised operation carries an idempotency key so that a retry never creates a duplicate.
  • If synchronisation is disabled or the instance is unreachable, the application behaves identically, and failed operations are queued and visible to an Admin.

6.9 Audit

Every change to an incident, status, assignment, alert rule, on-call schedule and runbook writes an audit entry recording who, what, when, and the values before and after. The API offers no update or delete path for audit entries, and the database role used by the application has no permission to modify them.

  • Identity: User, Team, Membership (with team-lead flag), Role assignment, On-call shift.
  • Telemetry: Service, Metric sample, Log entry, Change event.
  • Alerting: Alert rule, Alert, Threshold proposal.
  • Incidents: Incident, Status event, Team task, Attachment, SLA policy, Notification log, Escalation record.

  • AI evaluation: Prediction, Prediction feedback, Benchmark set.
  • Governance and integration: Audit entry, ServiceNow sync record.

7.3 Design principles

  • Server-side enforcement. State transitions, permissions, mandatory fields and closure rules are enforced in the API, never only in the interface.
  • Degrade gracefully. Failure of the LLM, ServiceNow or email provider must not block the core incident workflow.
  • Configuration over code. LLM provider, SMTP target, SLA values, retention and taxonomy are configuration.
  • Reproducibility. One command starts the system from a clean clone, and every quoted metric can be regenerated by a script.
  • Documented decisions. Each significant decision is recorded as an architecture decision record.

11. Defaults and open items

11.1 Assumed defaults

These values were proposed during requirements gathering and have not been objected to. They are adjustable by configuration and remain open to revision.

  • SLA targets: as in section 6.4.
  • Escalation timer: 10 minutes for P1 and P2.
  • Root cause taxonomy: Code or deploy, Configuration, Capacity or infrastructure, Dependency or third party, Data, Security, Process or human.
  • LLM provider: Claude first, behind the provider interface, with a second provider stubbed to prove swappability.
  • Retention: 30 days for metrics and logs; indefinite for incidents, runbooks and audit.
  • Permission matrix: as in section 5.

11.2 Open items

  • Final confirmation of the permission matrix, in particular who may change severity.
  • The numeric accuracy target for check G6.3, to be fixed before the evaluation is run.
  • The coverage floor for check G9.1.
  • ServiceNow field mapping between the application's incident model and the Table API.
  • Names and addresses of the demo teams and their group emails.
  • Buffer size and retry policy for the collector agent.
  • Decision on WebSocket reconnect and back-pressure behaviour for slow clients.
